# BatchFence candidate quickstart

Version0.3.0-rc.1 is a private/local engineering candidate. Public web and stable Windows remain0.2.0: https://batchfence.onrender.com and https://github.com/NuraliKuzhagaliev/BatchFence/releases/tag/v0.2.0. Candidate source: https://github.com/NuraliKuzhagaliev/BatchFence/pull/1. No real inventory actions.

From D:\projects\BatchFence, existing private pilot: `docker compose -f ops/compose.pilot.yml up --build -d`. Open http://127.0.0.1:8788. First setup uses `python -m scripts.pilot-config` then named-user provisioning in docs/enterprise/pilot-operations.md. Existing config is preserved. The candidate Windows installer defaults to this private backend and requires it running. Create your own distinct reviewer and release-approver accounts; engineering test accounts are not accepted identities.

Start in Incidents. Load a disclosed synthetic example or import your owner-approved records. Use Sources & intake to map columns and inspect originals. Review every model candidate and unresolved scope before calculating/approving. The persistent quantity strip separates proposed hold, applied hold, pending recovery and confirmed recovery.

Signals: review/freeze comparable baseline observations, inspect variable control limits, open a linked investigation. Knowledge: approve an applicable source revision, inspect exact cited proposals, then separately review the evidence for a case check. Recovery: review policy, authenticity and whole-pool inspection, prepare exact restrictions, obtain a distinct approval, execute workspace recovery and inspect its separate receipt. Another incident's hold remains. Actions: investigate, freeze future effectiveness criteria, record implementation, collect comparable follow-up and explicitly review outcome or recurrence.

Export a packet before leaving the free public service. Offline packets are historical and cannot authorize actions. Original scanned images require the backed-up source store. The candidate Linux profile supports OCR; Windows uses that backend. Actual OS chooser/save/reopen and independent operator/domain acceptance are still required.

Live AMD for new tasks remains blocked until the existing configured endpoint/model has confirmed zero-cost allowance. Keep keys in private environment files only. Fixture, historical replay and fresh inference must stay visibly separate.
